# Recognition algorithm

## What this is, and what it is not

This system performs **template-based speaker + passphrase verification**. It
answers one question: *does this 1.6 seconds of audio have the same acoustic
shape as the utterance I was trained on?*

It is **not** speech-to-text. It never recovers the Persian words «پارکینگ باز
شو», it has no phoneme model, no language model and no dictionary. If you
trained it on someone humming a tune, it would accept the tune. The passphrase
matters only because a different phrase produces a different sequence of
spectra and energies over time, and that difference shows up in the distance.

Read [the limitations section](#limitations) before you claim anything about it.

## Pipeline

```
8 kHz samples
   |
   +-> 64-sample frames (8 ms)
         |
         +-> Hamming window, Q15                     -> fft64_window()
         +-> 64-point fixed-point FFT                -> fft64()
         +-> |X[k]| ~ max + min/4 for k in a band    -> fft64_magnitude()
         +-> sum x^2          (short-time energy)
         +-> sign changes     (zero-crossing count)
         |
   +-> accumulate into 8 temporal segments of 25 frames (200 ms each)
         |
   +-> normalise to 8 segments x 10 features, each 0..255
         |
   +-> 80-byte feature vector
```

1.6 s at 8 kHz is 12800 samples, which will never fit in 2 KB of SRAM. Nothing
is ever stored at sample rate: each frame is folded into the accumulators for
its segment and then discarded. Peak working set is one 64-sample frame plus a
304-byte accumulator block.

## Frame and segment arithmetic

| Quantity | Value | Derivation |
|---|---|---|
| Sample rate | 8000 Hz | Timer2 CTC, /8, OCR2A = 249 |
| Frame length | 64 samples | one FFT |
| Frame duration | 8.0 ms | 64 / 8000 |
| Capture window | 1.6 s | the assignment's figure |
| Frames per capture | 200 | 1.6 s / 8 ms |
| Segments | 8 | the assignment's figure |
| Frames per segment | 25 | 200 / 8 |
| Segment duration | 200 ms | 25 x 8 ms |
| FFT bin width | 125 Hz | 8000 / 64 |

## The FFT

Adapted from Bruce Land's ECE4760 fixed-point FFT (Cornell), itself derived from
Tom Roberts' 1989 `fix_fft` as revised by Malcolm Slaney in 1994. Full
attribution is in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md); the
changes and their reasons are listed at the top of `src/fft64.cpp`. In short:

* **128 points to 64 points.** One FFT now covers exactly one 8 ms analysis
  frame, and the two working buffers cost 256 bytes instead of 512. On a chip
  with 2 KB of SRAM that is not a marginal saving.
* **Twiddles moved to PROGMEM.** The original builds a sine table at boot with
  floating-point `sin()`, which pulls in libm and spends 256 bytes of SRAM. The
  table is now generated by `tools/gen_tables.py` and lives in flash.
* **Q8.8 inline assembler replaced with C Q15.** The assembler `multfix` macro
  is faster, but the C version compiles for the host as well as the AVR, which
  is what lets `test/host_tests.cpp` verify the transform. The measured cost of
  window + FFT is 20908 cycles = 1.31 ms, against an 8 ms budget - there was no
  need to spend the readability.

**Scaling.** Every butterfly stage divides its output by two, so the result is
the true DFT divided by 64 and no intermediate can exceed the largest input.
That is what makes the transform overflow-proof in `int16_t` with no
block-floating-point bookkeeping. Because the centred ADC value only spans
±512, the windowed input is pre-scaled left by `FFT_INPUT_SHIFT` = 4 bits before
the transform; without it, the quiet bins would be quantised away. Worst-case
bin magnitude is then 8192 / 2 = 4096, comfortably inside `int16_t`.

**Magnitude.** `|X| ≈ max(|re|,|im|) + min(|re|,|im|)/4`. The exact
`sqrt(re² + im²)` would cost a 32-bit square root per bin per frame. The
approximation is exact on the axes and worth up to +11.8% at 45°. Because the
same approximation is applied when the template is trained and when a test
utterance is scored, the bias cancels in the distance.

## Frequency bands

Bin *k* is centred on *k* × 125 Hz. Bins 0..31 are the usable half.

| Band | Bins | Frequency | Width |
|---|---|---|---|
| 0 | 2..3 | 250 – 375 Hz | 250 Hz |
| 1 | 4..5 | 500 – 625 Hz | 250 Hz |
| 2 | 6..7 | 750 – 875 Hz | 250 Hz |
| 3 | 8..10 | 1000 – 1250 Hz | 375 Hz |
| 4 | 11..13 | 1375 – 1625 Hz | 375 Hz |
| 5 | 14..17 | 1750 – 2125 Hz | 500 Hz |
| 6 | 18..22 | 2250 – 2750 Hz | 625 Hz |
| 7 | 23..28 | 2875 – 3500 Hz | 750 Hz |

Reasoning:

* **Bins 0 and 1 are excluded.** Bin 0 is DC - the residual of the 2.5 V bias
  and any drift in the divider. Bin 1 is 125 Hz, which is where mains hum and
  its harmonics live. Neither carries speech.
* **The top stops at 3500 Hz.** Nyquist is 4000 Hz and the input RC filter
  corners at 3.4 kHz (see [adc.md](adc.md)), so anything above this is a mixture
  of attenuated signal and whatever aliased in.
* **The bands widen with frequency.** This is the idea a mel filterbank
  encodes: human frequency resolution is much finer at the low end. Equal-width
  bands would spend three quarters of the feature budget on the region above
  2 kHz, where speech carries the least identifying information.

## Features

Ten per segment, eighty per utterance, one unsigned byte each.

| Index | Feature | Raw accumulator | Range before normalisation |
|---|---|---|---|
| 0 | short-time energy | Σ x² over 1600 samples | 0 .. 4.19e8 |
| 1 | zero-crossing count | sign changes over 1600 samples | 0 .. 1600 |
| 2..9 | band level | Σ bin magnitudes over 25 frames | 0 .. ~6.1e5 |

Eight bits per feature is plenty: the distance metric only needs a ranking, and
the measurement noise between two recordings of the same phrase is far larger
than 1/255 of full scale. It also makes the EEPROM record 90 bytes instead of
250.

## Normalisation

The three quantities have wildly different units. They all have to land on one
0..255 scale or the distance is dominated by whichever is numerically largest.

**Energy** → `255 · sqrt(E[s] / Emax)`, where `Emax` is the maximum over the
eight segments of *this* utterance.

* Per-utterance, so the same phrase spoken loudly and quietly produces the same
  contour. Without this the lock is a volume meter and will admit anyone who
  shouts.
* The square root moves the value from the power domain to the amplitude
  domain. Speech energy has a huge dynamic range; a linear scale crushes every
  quiet segment to 0 and throws away the contour that distinguishes phrases.
* Implemented as `vpl_isqrt(255² · E / Emax)`, so there is no floating point
  and no division by a value that can be zero.

**Zero-crossing count** → `255 · min(1, Z[s] / 800)`, a *fixed* scale.

ZCR is already loudness-invariant, and its absolute value carries phonetic
information - a fricative crosses zero far more often than a vowel. Rescaling
it per utterance would destroy exactly that. 800 crossings in 1600 samples is a
2 kHz dominant frequency, comfortably above voiced speech and near the top of
the fricative range, so it is a sensible full-scale point. Above it the value
saturates rather than wrapping.

**Band levels** → `255 · B[s][b] / Bmax`, where `Bmax` is the maximum over
*all* segments and bands of this utterance.

* One global maximum rather than a per-segment one. Normalising each segment
  against itself would amplify the noise in a silent segment to full scale and
  make silence look like speech.
* No square root here: these are already magnitudes, not powers.

All scaling is done by `scale_to()`, which halves both operands until the
product cannot overflow 32 bits. That costs at most one bit of ratio precision,
which is far below the 1/255 quantisation the result is heading for.

## Distance

```
distance = Σ over i of weight(i) · |input[i] − template[i]|
```

| Feature | Weight | Share of one segment's vote |
|---|---|---|
| energy | 3 | 23% |
| zero-crossing rate | 2 | 15% |
| each band (×8) | 1 | 62% total |

Without weighting, the eight band features outvote the two temporal ones 8:2
and the phrase contour barely matters. Broadly, the spectrum carries *who* is
speaking and the temporal contour carries *what* they said, and this system has
to get both right, so neither may dominate completely.

Manhattan rather than Euclidean: absolute differences are single-instruction on
an AVR, there is no square root, and the ranking they produce is exactly what a
threshold test needs. Maximum possible distance is
`8 × (3 + 2 + 8) × 255 = 26520`, which is `DISTANCE_MAX` in `config.h`.

## Training

Three utterances from the same speaker saying the same phrase.

```
template[i] = round( (F1[i] + F2[i] + F3[i]) / 3 )
```

Accumulated in `uint16_t` - three 0..255 values sum to 765, which does not fit
in the `uint8_t` being averaged. Rounding is to nearest, so repeated retraining
does not drift the template downwards.

Only two of the three vectors are stored (`g_train[2][80]`, 160 bytes); the
third is the freshly captured `g_feature`. That saves 80 bytes over keeping all
three.

## Threshold calibration

The threshold is **measured**, not chosen:

```
spread    = max over i of distance(Fi, template)
threshold = spread × 2 + 1060,  clamped to at most 7956
```

* `spread` is measured **against the template**, not pairwise between the
  utterances, because distance-to-template is exactly the quantity the
  test-time comparison produces. A pairwise spread is roughly twice as large
  and would need a different margin to mean the same thing.
* **×2 safety margin.** The three training utterances sample the speaker's
  variability; doubling it turns "how much does this speaker vary" into "how
  much variation do we accept".
* **+1060 floor** (4% of `DISTANCE_MAX`, i.e. an average deviation of ~10 codes
  out of 255 per feature). Three recordings made back to back can be almost
  identical, giving a near-zero spread and a threshold so tight the authorised
  speaker fails on the very next attempt.
* **7956 ceiling** (30% of `DISTANCE_MAX`). If the training utterances disagree
  by more than this, the recording session was bad. Accepting a threshold that
  loose would make the lock meaningless, so the firmware clamps and prints
  `WARNING: THRESHOLD CLAMPED` so the operator knows to retrain.

The three training distances are printed at the end of training. They are the
single most useful diagnostic in the system: if they are large, the recordings
disagree and no threshold will rescue the result.

## Measured behaviour

`test/host_tests.cpp` drives the real feature extractor with synthetic
utterances - a fixed sequence of formant-like tones per segment - and checks
the six scenarios from the assignment. A representative run:

| Case | Distance | Result |
|---|---|---|
| threshold from training | 1516 | — |
| authorised speaker + correct phrase | 36 | ACCEPT |
| same, at 1/4 the volume | 246 | ACCEPT |
| authorised speaker + wrong phrase | 6602 | REJECT |
| different speaker + correct phrase | 3567 | REJECT |
| silence | 7356 | REJECT |
| broadband noise | 12276 | REJECT |

These are synthetic signals and the separation is much cleaner than real speech
will give. They prove the arithmetic is right and the normalisation is doing
its job; they do not predict accuracy on human voices.

## Limitations

Be honest about these in any report or demonstration.

1. **No time alignment.** Segments are fixed 200 ms windows from the moment the
   VAD fires. Say the phrase 15% faster and every segment boundary lands
   somewhere different, and the distance grows for a reason that has nothing to
   do with identity. Dynamic time warping is the standard fix and does not fit
   in 2 KB alongside everything else.
2. **The capture window is fixed at 1.6 s.** A shorter utterance is padded with
   whatever follows it; a longer one is truncated.
3. **Speaker and phrase are entangled.** One distance covers both. The system
   cannot tell you *why* it rejected - wrong person, wrong words, or just a bad
   recording.
4. **Eight bands is very coarse.** Cornell's version used 32 mel filters and a
   DCT to decorrelate them; this one uses eight raw band sums, which are
   correlated with each other and with the energy feature.
5. **The VAD trigger is not the start of the word.** Speech is confirmed after
   `VAD_START_FRAMES` frames, and the frame that triggered it is captured, so
   roughly 16 ms of the leading consonant is lost. That is consistent between
   training and testing, so it does not bias the comparison, but it does mean a
   word beginning with a soft fricative starts partway in.
6. **One template, one speaker.** There is no cohort, no impostor model and no
   score normalisation, so the threshold is calibrated only against the
   authorised speaker's own variability.
7. **The published accuracy of the far more sophisticated Cornell system was
   77–83% correct unlock.** Expect less from this one. It is an ADC/DAC/PWM
   teaching platform that happens to recognise speech, not a security product.
